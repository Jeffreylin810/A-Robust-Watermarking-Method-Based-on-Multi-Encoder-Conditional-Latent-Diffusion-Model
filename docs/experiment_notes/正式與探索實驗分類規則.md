# 正式與探索實驗分類規則

更新日期：2026-06-11

## 一、先說結論

在每個實驗執行前，必須先標記為以下其中一類：

| 代號 | 類型 | 用途 | 可否直接作為第四章最終數據 |
|---|---|---|---|
| `E` | 探索／開發實驗 | 找 loss、steps、checkpoint、模組階段與失敗原因 | 否；只能作方法發展、消融設計與限制分析 |
| `F` | 正式第四章實驗 | 驗證執行前已鎖定的研究問題與方法 | 可以 |

未先標記類型、未寫正當性或執行途中改變比較條件的實驗，一律視為 `E`。

目前反覆使用的 COCO `unseen eval1000` 已參與 Stage、loss、checkpoint 與模組
候選選擇，因此從現在起統一稱為：

```text
dev1000
```

它與 train10000 沒有圖片重疊，所以既有結果不是無效；但它已不是完全未被查看的
最終測試集。既有 Experiment 1-9 應視為開發／驗證結果，而不是第四章最終主表。

正式第四章主結果改用：

```text
COCO test2017 finaltest1000_locked
```

此資料只允許在方法、checkpoint、metric 與 attack protocol 全部鎖定後評估。

## 二、Checkpoint 的正當性

正式比較不是要求不同方法使用同一個 checkpoint；不同方法本來就有不同參數。
真正要避免的是：

1. 故意選一個訓練失敗的 baseline checkpoint。
2. 看過 final test 結果後，反覆更換 checkpoint 直到數字好看。
3. 對自己的方法挑最佳 checkpoint，卻對 baseline 隨便挑一個 checkpoint。
4. 把探索中失敗的版本包裝成正式 baseline。

每一個正式 checkpoint 必須在執行 final test 前通過以下健康檢查：

- 完成預先規定的訓練 steps / epochs。
- 無 NaN、崩潰或中途截斷。
- 使用預先規定的 `final checkpoint`，不依 final test 選 best checkpoint。
- 訓練 config、資料 manifest、seed、程式版本與 SHA-256 可追溯。
- 若是官方／基準方法，優先採作者公開 recipe；無法完全重現時明確標為 local reproduction。
- 若方法 recipe 由探索得到，可以用 dev1000 選定；一旦鎖定便不得再根據 finaltest1000 修改。

因此，正式測試結果很差不等於 checkpoint 不合理。只要 checkpoint 是按預先鎖定
規則產生、訓練健康且沒有 test-set selection，差的結果就是應該如實報告的結果。

## 三、正式實驗執行前必填

每個 `F` 實驗都必須先建立一份 manifest，至少包含：

```text
實驗代號：
分類：F（正式第四章）
研究問題：
論文主張邊界：
比較角色：
固定 checkpoint 與 SHA-256：
固定 train manifest 與 SHA-256：
固定 final-test manifest 與 SHA-256：
唯一允許改變的變因：
固定 metrics：
固定非幾何 attack suite：
預先指定 seeds：
checkpoint 選擇規則：
失敗／重跑規則：
輸出資料夾：
```

正當性必須回答：

1. 為什麼這些方法是合理的比較角色？
2. 哪些外部條件完全相同？
3. 哪些是方法固有差異，為什麼不能強制相同？
4. checkpoint 如何選定，是否在查看 final test 前完成？
5. 這個結果允許支持什麼主張，又不能支持什麼主張？

## 四、探索實驗規則

`E` 實驗允許：

- 使用 dev1000 比較候選。
- 調整 loss、steps、curriculum 與模組權重。
- 提前停止不合格候選。
- 根據結果規劃下一個候選。

但必須明確標示：

```text
此為探索／開發結果，不直接填入第四章最終主表。
```

探索結果可以在論文中作為：

- 方法設計脈絡。
- 消融候選的來源。
- 失敗分析與限制。
- 決定正式 recipe 的依據。

若要將探索中某個消融數字放入第四章正式表，必須先把所有要比較的變體一起鎖定，
再於 finaltest1000 上重新評估一次。

## 五、正式測試的禁止事項

- 不可用 finaltest1000 做 hyperparameter tuning。
- 不可依 finaltest1000 選 checkpoint 或 early stopping。
- 不可看到結果後修改 attack 參數再宣稱同一正式實驗。
- 不可只重跑自己的方法、不重跑受影響的 baseline。
- 不可把 dev1000 與 finaltest1000 的數字放在同一欄卻不標明 split。

程式錯誤、檔案遺失或 GPU 中斷可以按完全相同設定重跑；任何會改變研究問題或模型
行為的修改，都必須退回 `E` 階段。

## 六、目前結果重新分類

| 既有內容 | 新分類 | 保留價值 |
|---|---|---|
| VAE、loss、Stage A/B/C、V1-V7 | `E` | 方法形成與失敗分析 |
| refine2000/5000/10000、Experiment 2b-7b | `E` | recipe、泛化與消融候選 |
| Experiment 8 速度成本 | 暫定 `E`／預備數據 | 方法完全凍結後可用相同 artifact 再確認 |
| Experiment 9 三方法比較 | `E`：受控開發集比較 | 證明三角色可在相同 protocol 下執行；不能當最終 test 主表 |
| 新的 M01 finaltest1000 比較 | `F` | 第四章正式方法比較 |

```text
方法開發與正式 protocol 準備已完成大部分；

```
